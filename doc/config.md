# Editing bridge.yaml

`bridge.yaml` (at `~/.config/bridge/bridge.yaml` unless `-c` names another) is the whole configuration: there is
no other state to keep in sync. You, or a coding agent, edit
the file; `bridge check` says whether it is valid and what the edit changes; a running bridge applies it on save.
Edits that widen access wait until an owner confirms them.

The machine-readable schema is [schema.json](schema.json) (generated by `bridge schema`).
`bridge init` writes a first line that points editors with YAML language support at it:

```yaml
# yaml-language-server: $schema=/path/to/bridge/doc/schema.json
```

## The loop

1. Edit `bridge.yaml`.
2. Run `bridge check` (or `bridge check --json`). It lists every problem as `bridge.yaml:<line>: <key path>: <message>`,
   runs the file's `tests`, and lists what changes against the config the bridge applied last:
   `+` widens access, `-` narrows it, `~` neither.
3. Save. A running bridge reloads on its own:
   - nothing widens access, so it applies at once;
   - something widens access, so the bridge keeps the running config and asks every owner (`trust: owner`) to
     confirm it. Owners get Apply / Reject buttons in their direct messages with the bot. The dashboard shows
     the change too, and `bridge check --apply` confirms it from this machine.
   - the file is invalid or a test fails, so nothing changes and the bridge logs why.
4. A restart does not skip the confirmation: the bridge starts with the config applied last, then asks again. If
   that record can't be read (a newer schema dropped a setting it has), the bridge doesn't start until
   `bridge check --apply` confirms the file as a whole.

The bridge records the text it applied in `~/.bridge/applied/`. Every applied, held or rejected change is in the
audit trail (`bridge trace`, kind `config`). A change waits as a whole, so an edit that both removes and adds a
route keeps the old routes until it is confirmed.

What widens access:

| Change | Why |
| --- | --- |
| A route is added or changed, or routes are reordered | Routes match top to bottom, so a message may reach another agent |
| A person, agent, tool server or IM connection is added or changed | A new id, command, URL or token reaches further |
| For an agent or tool server, only a setting that can reach further | `description`, `timeout` and `model` never do; `permission_mode` and `sandbox` only toward more access; `allowed_tools` only with a new tool; `worktree` only when turned off. Anything else (`command`, `cwd`, `url`, `headers`, `env`, …) does |
| A policy is removed or changed, or a new policy names approvers | An approval or limit is lifted, or more people may approve |
| `defaults.max_hops` goes up, `defaults.external_budget` loosens (more `usd`, a shorter `per`, or `off`), or `server.host` changes | Delegation goes further, strangers may spend more, or the dashboard listens beyond this machine |

Removals and new limits apply at once, and so do housekeeping settings such as `progress`, `retention` and the
other `defaults`.

The confirmation guards against edits nobody meant to make, such as a prompt-injected agent changing routes. It is
not a sandbox: an agent that can run arbitrary commands as you can do anything you can, including confirming its
own change. Keep agents that run through the bridge on a permission mode and tool list that need your approval for
shell commands (Claude Code's `permission_mode` and `allowed_tools`), or in a sandbox that keeps their writes off your
checkout (Codex's `sandbox`: `read-only`, or `workspace-write` with `worktree: true`).

## Routes

A message reaches an agent only through a route (deny by default).

- An IM route (`from: slack:#dev`, `slack:dm`, `slack:*`) goes to exactly one agent. A route to an agent that runs
  on this machine (`claude-code`, `codex`, `stdio`) must name `when.sender`: a list of people, or `anyone` to opt
  out on purpose. With `anyone`, a stranger's message drives that agent's own tools (shell, file edits), which never
  pass through the bridge; only its bridge tools and delegation wait for an owner (see Policies). Keep such an
  agent on `permission_mode: plan` or `sandbox: read-only`.
- `when.mention`: `true` (the default) needs the bot @-mentioned in a channel; a DM always counts as mentioned.
  `false` takes every message in the channel. `<agent>` needs the mention *and* the agent's name at the start
  (`@bot data-agent …`), so several agents can share a channel.
- A message that starts with an agent's name (`codex fix the login`, `@bot codex …`) is for that agent only.
- A message that names no agent stays with the agent already holding the conversation (the thread, or the DM until
  `dm_idle_reset`): that agent's routes are tried first, and each must still match. Otherwise routes are tried top
  to bottom and the first that matches wins. Each agent keeps its own session in the conversation: switching back
  resumes it, with a short note of the other agents' messages and replies since its last reply (the newest 10,
  500 characters each, from the audit trail).
- A reply in a thread the agent already holds needs no mention.
- `reset` / `/new` starts fresh sessions for the thread, for every agent in it.
- A message meant for the bot (a DM, a mention, a reply to it) is always answered. When no route takes it, someone in
  `people` hears which agents here take their messages (`Start your message with \`claude-code\` or \`codex\``),
  or that none do. Anyone else hears one line that names no agent, at most once a day: the bot only answers people
  it is set up for, and the id to add for them. A message that has to wait for a turn in progress is answered
  `⏳ Queued`, saying whose turn it waits for and, when that turn waits for an approval or an answer, that answering
  it lets the conversation go on (until then nothing else in it runs, not even another agent); a sticker or other content the IM adapter can't pass on is answered `I can't read …`. Messages not
  meant for the bot that no route takes get no reply, so a busy channel never hears from it; other bots' messages
  are dropped by the IM adapters, so two bots never answer each other. Every ignored message is in the audit trail.
- An agent route (`from: <agent>`) lists what that agent may reach: other agents, and tools as `server.tool`
  globs.

## Policies

- A policy applies when every key of its `match` holds (`tool`, `agent`, `writes`); a missing key matches
  anything. `writes: true` matches tools the server doesn't mark read-only.
- Every applying policy counts: approvers are merged, and the shortest `timeout` (default `10m`) and the strictest
  `max_hops` / `budget_usd` win.
- `max_hops` and `budget_usd` belong to an agent, so they go on policies that match by `agent` only.
- Approvers are people whose trust is not `external`. `initiator` means whoever started the conversation, but only
  when that is such a person: for a message from someone outside `people:` (a `sender: anyone` route) or with
  trust `external`, the owners decide instead, so nobody approves their own request.
- Such a message's turn, and every agent it delegates to, is stricter even without a policy: each tool call that
  may write (not marked read-only) and each `delegate` waits for an owner (`timeout` 10m unless a matching policy
  sets one). Matching policies still add their approvers. Read-only tools, `send_message` and `ask_human` run as usual.
- `budget_usd` is per conversation; a conversation deleted by `retention` starts with a fresh budget.
- `defaults.external_budget` (`{ usd, per }`, default `{ usd: 2, per: 24h }`; `off` for none) caps what one sender
  outside `people:` (or listed with trust `external`) spends in any rolling `per` window, counted by IM account
  (`slack:U0123`, or the person id) across all their
  conversations and the agents they delegate to. Each turn gets the lesser of this and the conversation's budget,
  and starts only when that covers the agent's cheapest recent turn. Their turns run one at a time, so parallel
  threads can't overrun it. Over the limit they hear only "You've reached the usage limit for now. Try again in
  about …", once; until then their messages are dropped (each logged as `budget` in the audit trail) and the owners
  get one DM. After a restart that "once" starts over: one more message is refused and reported.

## Rules a check enforces

Besides the routing and policy rules above:

- Credentials never go in the file. Store them with `bridge secret set <name>` and write `secret:<name>`, or
  `env:NAME`; in a header write `Bearer ${secret:name}`. A value that looks like a token is an error.
- Names of agents and tool servers use letters, digits, `-` and `_`; an agent and a tool server can't share a name.

## Tests

`tests` holds assertions about the routes in the same file. They run on every load; a file whose tests fail is
not applied. Write one for every rule you rely on, especially who must *not* get through:

```yaml
tests:
  # A message from an IM address. sender: a person id, or a platform user id; leave it out for a stranger.
  - { from: "slack:#dev", sender: me, mention: true, expect: claude-code }
  - { from: "slack:#dev", sender: U0STRANGER, mention: true, expect: none }
  - { from: "feishu:dm", sender: me, expect: claude-code }
  # An agent calling a tool ("server.tool") or delegating to another agent.
  - { agent: claude-code, calls: github.create_issue, expect: allow }
  - { agent: claude-code, calls: data-agent, expect: deny }
```

`from` is `<im>:#channel`, `<im>:<channel id>` or `<im>:dm`; `mention` defaults to `false` (DMs always count as
mentioned); `text` defaults to `hello`. To see why a message routes the way it does, run
`bridge routes explain --from slack:#dev --sender me --mention`.

## Sections

| Section | Holds | Notes |
| --- | --- | --- |
| `people` | `<id>: { trust, slack, feishu, telegram, discord }` | `trust`: `owner`, `trusted`, `member` (default), `agent`, `external`. Platform ids: Slack member id, Feishu / Lark open_id, Telegram and Discord user id |
| `im` | `slack`, `feishu`, `telegram`, `discord` connections | Credentials as `secret:` / `env:` references; `feishu.domain`: `feishu` or `lark`; `discord.message_content`: ask for the privileged intent that `mention: false` routes need (default `false`). Changing them needs a restart |
| `agents` | `<name>: { type: claude-code \| codex \| webhook \| a2a \| stdio, … }` | claude-code: `cwd`, `permission_mode`, `allowed_tools`, `model`, `worktree`, `worktree_links`, `git_token`. codex: `cwd`, `sandbox`, `model`, and the same `worktree` settings. webhook: `url`, `headers`, `timeout`. a2a: `url` (agent card), `headers`, `timeout` ([doc/agents.md](agents.md#a2a-agents)). stdio: `command`, `args`, `cwd`, `env`, `timeout` |
| `tools` | `<name>: { command, args, env }` or `{ url, headers, oauth }` | MCP tool servers; `oauth: true` signs in with `bridge auth <name>` |
| `routes` | `{ from, when, to }` | `from`: an IM address or an agent. `when`: `mention`, `sender`. `to`: one agent (from IM), or agents and `server.tool` globs (from an agent) |
| `policies` | `{ match: { tool, agent, writes }, approve_by, timeout, max_hops, budget_usd }` | Every key of `match` must hold; all applying policies count and the strictest wins |
| `defaults` | `dm_idle_reset`, `offline_queue_ttl`, `progress`, `max_hops`, `max_file_mb`, `files_ttl`, `worktree_prune_after`, `retention`, `external_budget` | Housekeeping and limits |
| `server` | `host`, `port`, `data_dir` | The dashboard and MCP hub listen on `host:port`; the database is in `data_dir` (default `~/.bridge`; a relative path is from the config file's folder) |
| `tests` | Assertions, see above | |

The schema has every key with its default and a description.
